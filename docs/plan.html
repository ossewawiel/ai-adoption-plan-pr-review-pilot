AI in D&E: make it work, then make it better

The plan in short: one small platform team builds one plugin, and every team's AI tool loads it. In that way the guard rails, the know-how and the measuring arrive together. We start at code review, prove it on one team first, and only widen when the numbers show that it works.

Where I'm coming from

I have done this already, and the numbers show it

For a year and a half I used AI coding tools in my own time, and I learned the hard way what works and what does not. For the past eight months I have been doing it at my current employer, where we are busy replacing an old C++ desktop client with a web application. In the first six weeks we wrote no product code. We built proofs of concept, design guidelines and a showcase that convinced management to go ahead. After that the numbers started to climb.

To be honest about it. That was eight people on new code, in Kotlin. You have 60 developers on existing .NET systems. So I did not want to trust only my own experience, and I went to look at the hard evidence.

What the evidence says

Three findings that point in the same direction

AI makes a team more of what it already is

DORA 2025 asked nearly 5,000 people. Strong organisations get stronger with AI and struggling ones see their problems grow. Teams deliver more, but delivery also becomes less stable.

DORA, State of AI-assisted Software Development 2025

Feeling faster is not the same as being faster

In METR's trial early in 2025, experienced developers believed AI made them 20% faster, but the measurements showed they took 19% longer. METR says the result is out of date by now. The lesson I take from it is that we must measure.

METR trial · 2026 update

The companies that got far built the rails first

Spotify has already merged more than 1,500 pull requests written by agents, and it started with migrations. At Stripe it is more than 1,300 a week, and a person reviews every one.

Spotify · Stripe

The stance

One company plugin

Think of a new developer on the first morning. They install one thing, and from then on their AI assistant already knows our standards, will not open the secrets file, and reports what it costs.

That one thing is a Claude Code plugin: a package of rules, skills (ready-made recipes) and automatic checks. A small AI platform team owns it, and central settings keep it switched on. It is like the toolbox that is bolted to every bakkie, with the same tools and safety gear no matter who drives. In this way the tool itself enforces the standard, and we do not have to rely on a memo.

North star: agents write the code, and people own the specs, the architecture and the review.

A person stays accountable at every step, and the evidence shows that speed without gates costs stability.

Plugin 2

Plugin 1 on every team. Pipelines for small UI and API work where the design comes first.

The promise

On every team, small fixes, tests and migrations are written by agents and approved by people.
Beyond

The ultimate prize

From spec to pull request, done by agents by default. At this stage I am not putting a date on it.

The first 90 days, up close

Weeks 1–2 · measureWe take the baseline from git, Jira and the pipelines, run the first survey and hand in the security pack.
Weeks 3–6 · start smallA pilot group of 6 to 8 starts: one product team with its QA and BA. They use Plugin 1 every day, and we hold the first workshop.
Weeks 7–12 · prove itThe Issue lane runs. We publish the first scorecard against the baseline, run the second survey, and then decide to widen, adjust or stop.

Why start at review and testing?

Copilot already helps there, so it is a small first step. The gates must also be in place before the speed arrives. It is like a braai, where you get the fire right before the meat goes on. And the pilot in this repo is a review tool, so it is already a working piece of Plugin 1.

Build, buy or SaaS?

We buy the model and the agent runtime. We build only the thin layer that holds our own standards, and that is the plugin. We take SaaS only when the vendor passes the same security pack. Three questions decide it: does it set us apart, does data leave South Africa, and what will it cost us to leave again?

1b. Rolling out Claude Code under strict security

The first thing security will ask: what leaves the building?

What I put in front of security

  1. A picture of exactly what leaves a developer's machine, and where it goes.
  2. The vendor's retention terms, in writing.
  3. Our answer to POPIA section 72. Personal information may not go to a third party in a foreign country unless one of the listed grounds applies, and location information counts as personal. We must plan for the model running outside South Africa, so no personal information may reach a prompt.
  4. The managed settings: what the agent may read and run, the plugin lock, and the usage export.
  5. The scope of the pilot, and how we switch it off.

The risks I expect, and the control for each one

Personal data or secrets in a promptA redaction step, and a hook that blocks the read
Instructions hidden in repo contentCode is treated as data, and a person reviews every change
An agent with too many permissionsManaged settings with a short allow-list and no bypass mode
Cost that runs awayA model pinned to each job, and spend on the scorecard
Tools that nobody approvedOnly the approved plugin source is allowed

The house rules

  1. No personal information or secrets in a prompt.
  2. A person reviews and owns every change, and an agent never approves its own work.
  3. Agent code goes through the same pipeline gates as everybody else's.
  4. Only approved tools, models and plugins.
  5. Say so when an agent wrote it.

Making them stick: four layers, from strongest to weakest

  • Managed settings that nobody can override
  • Hooks that block an action before it happens
  • Gates that fail a build
  • Review by a person

When a rule is missing, we add the rule and a check for it. A reminder email does not fix it.

1b, continued. People, rollout and Copilot

Bring the people along

Every weekA short bulletin goes out. AI drafts it from the merge history, a person sends it, and it sounds like us. It may tease the work but never the person.
Every monthA team shows one thing that worked and one that did not, in a workshop.
Every quarterWe run a survey on confidence, friction and trust.

Rollout and stepping out

The pilot group learns by doing its own tickets with the plugin. Each new team then gets a champion trained by the pilot group. I can step out when D&E people run the plugin releases, every team has a champion, and somebody else publishes the scorecard.

Copilot

It stays until Claude Code is approved. The pilot group then uses both for one cycle and reports the difference. Teams move over at licence renewal, so nobody pays double for long.

Design

Plugin 2 brings design skills: one library of screen building blocks and brand rules, with a critic step, so that screens built by AI still look like one product.

1c. Measuring adoption, value, quality and cost

One scorecard per team, and no league table

Baseline and return

Four to six weeks of history give us the baseline, and we compare the pilot group with teams that have not started.

return = hours saved × loaded cost − licences − platform team

I report the measured speed and not how fast it feels.

A red robot means the team needs help

It is not there to blame anybody.

Low use and low trust: we pair with them.
High use and more failures: we tighten the gates.
A high cost per change: we look at the model mix.

What I am assuming

Four assumptions

Security approval comes by about week 3. If it is later, we make a plan: the dates move and the pilot group applies the same standards with Copilot.
Tests and pipelines are in a fair state. If not, tests come first.
The company holds customer location data, so POPIA applies, and compliance must confirm any other regulator.
The milestones run to month 12, as the brief asks. Month 18 is where they lead to.

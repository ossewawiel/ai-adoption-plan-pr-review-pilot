AI in D&E: make it work, then make it better

One small platform team builds one plugin. Every team's AI tool loads it, so the guard rails, the know-how and the measuring all arrive together. We start at code review, prove it on one team, and widen when the numbers say so.

Where I'm coming from

I've run this play, and the numbers moved

Before any of this was my job, I spent a year and a half using AI coding tools on my own time, learning the hard way. For the past eight months I've done it for real at my current employer, replacing an old C++ desktop client with a web application. The first six weeks held no product code: proofs of concept, design guidelines, and a showcase that won the go-ahead.

What the evidence says

Three findings, and they point the same way

AI is an amplifier

DORA 2025 asked nearly 5,000 people. AI magnifies what a strong organisation does well and what a struggling one does badly. Throughput goes up; so does instability.

DORA, State of AI-assisted Software Development 2025

Feeling fast isn't being fast

In METR's early-2025 trial, experienced developers reckoned AI had made them 20% faster. The stopwatch said they took 19% longer. METR now calls that result out of date, but the lesson holds: measure, don't guess.

METR trial · 2026 update

The ones who got far built the rails first

Spotify has merged more than 1,500 agent-written pull requests, starting with migrations. At Stripe, over 1,300 a week are agent-written, each reviewed by a person.

Spotify · Stripe

The stance

One company plugin

Picture a developer's first morning. They install one thing, and from then on their AI assistant knows our standards, refuses to open the secrets file, and reports what it costs.

That one thing is a Claude Code plugin: rules, skills (ready-made recipes for a task) and automatic checks, owned by a small AI platform team and locked on by central settings. It's the toolbox bolted to every bakkie: same tools, same safety gear, whoever's driving. The standard is enforced by the tool, not by a memo.

North star: agents write. People own the specs, the architecture and the review.

A person stays accountable at every step, and speed without gates costs you stability.

The first 90 days, up close

Weeks 1–2 · measureBaseline from git, Jira and the pipelines. First survey. The security pack goes in.
Weeks 3–6 · start smallA pilot group of 6 to 8: one product team with its QA and BA. Plugin 1 in daily use. First workshop.
Weeks 7–12 · prove itThe Issue lane runs. First scorecard against the baseline. Second survey. Then we decide: widen, adjust or stop.

Why start at review and testing?

Copilot already helps there, so it's a small first step. Gates must exist before the speed arrives: you get the fire right before the meat goes on. And the pilot in this repo is a review tool, a working piece of Plugin 1.

Build, buy or SaaS?

Buy the model and the agent runtime. Build only the thin layer that holds our standards: the plugin. Take SaaS only when the vendor passes the same security pack. Three questions settle it: does it set us apart, does data leave South Africa, and what does it cost to leave?

1b. Rolling out Claude Code under strict security

Security's first question: what leaves the building?

What I put in front of security

  1. A picture of exactly what leaves a developer's machine, and where it goes.
  2. The vendor's retention terms, in writing.
  3. Our answer to POPIA section 72. Personal information may not go to a third party in a foreign country unless a listed ground applies, and location information counts as personal. Plan on the model running outside South Africa, so no personal information reaches a prompt.
  4. The managed settings: what the agent may read and run, the plugin lock, the usage export.
  5. The pilot's scope, and how we switch it off.

Risks I expect, and what stops each one

Personal data or secrets in a promptA redaction step, and a hook that blocks the read
Instructions hidden in repo contentCode is treated as data; a person reviews every change
An agent with too many permissionsManaged settings: a short allow-list, no bypass mode
Runaway costA model pinned to each job; spend on the scorecard
Tools nobody approvedOnly the approved plugin source is allowed

The house rules

  1. No personal information or secrets in a prompt.
  2. A person reviews and owns every change. An agent never approves its own work.
  3. Agent code passes the same pipeline gates as everyone else's.
  4. Approved tools, models and plugins only.
  5. Say when an agent wrote it.

Making them stick: four layers, strongest first

  • Managed settings nobody can override
  • Hooks that block an action before it happens
  • Gates that fail a build
  • Review by a person

A missing rule gets a rule and a check, not a reminder email.

1b, continued. People, rollout and Copilot

Bring the people along

WeeklyA short bulletin: AI drafts it from the merge history, a person presses send, and it sounds like us. It teases the work, never the person.
MonthlyA workshop: one thing that worked, one that flopped.
QuarterlyA survey on confidence, friction and trust.

Rollout and stepping out

The pilot group learns on its own tickets, not on slides. Each later team gets a champion the pilot group trained. I'm done when D&E people run the plugin releases, every team has a champion, and someone else publishes the scorecard.

Copilot

It stays until Claude Code is approved. The pilot group runs both for one cycle and reports the difference. Teams move over at licence renewal, so nobody pays twice for long.

Design

Plugin 2 carries design skills: one library of screen building blocks and brand rules, plus a critic step, so AI-built screens look like one product.

1c. Measuring adoption, value, quality and cost

One scorecard per team, and no league table

Baseline and return

Four to six weeks of history set the baseline, and the pilot group is compared with teams that haven't started.

return = hours saved × loaded cost − licences − platform team

I report measured speed, not felt speed.

A red robot means "send help", not "send blame"

Low use, low trust gets pairing time.
High use, rising failure rate gets tighter gates.
High cost per change gets a look at the model mix.

What I'm assuming

Four assumptions

Security approval lands by about week 3. If later, the dates slide and the pilot group applies the same standards with Copilot.
Tests and pipelines are in fair shape. If not, tests come first.
The company holds customer location data, so POPIA applies. Compliance confirms any other regulator.
The milestones run to month 12. Month 18 is where they lead.
